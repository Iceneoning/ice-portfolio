# UE 技术案例标准模板

> 一项目一篇；格式兼容 MDX，禁止从宣传语反推不存在的技术结果。具体 metadata 字段见 [内容模型](../architecture/02-content-model.md)。

## 1. 一屏讲清楚

- **项目名称 / 版本与状态**：游戏类型、引擎版本、当前阶段。
- **一句话项目目标**：做什么，不以纯技术名词代替项目目标。
- **本人负责**：列出系统边界，注明复用或协作部分。
- **观看方式**：封面、30–60 秒真实录屏、必要的字幕/短说明。
- **可验证入口**：公开代码、设计图、测试报告或演示，缺失则明确写「未公开 / 尚未验证」。

## 2. 问题背景

- 具体使用场景、玩家体验、架构约束和既有问题。
- 为何需要这个功能；替代方案是什么。
- 性能、网络、生命周期、资源一致性等限制仅在真正涉及时讨论。

## 3. 系统设计

推荐讲述顺序：需求 → 责任边界 → 组件关系 → 数据流 → 设计取舍。

示例结构（不是任何项目的事实陈述）：

```text
输入 / 玩法事件
    → 系统入口与合法性校验
    → 核心逻辑（状态 / 权限 / 生命周期）
    → 对外事件或持久数据
    → 客户端表现与 UI
```

配图标明哪个对象发起、哪个系统负责、哪些失败需要回滚；图中不可为了好看虚构不存在的类或事件。

## 4. 技术实现细节

每个细节按以下格式写：

1. **挑战：** 原本面临什么可观察问题？
2. **方案：** 使用哪些具体 UE/C++ 机制，为什么？
3. **边界：** 生命周期、网络权限、失败路径、性能、清理工作如何处理？
4. **证据：** 精简代码/实机录屏/测试日志及对应的版本或路径。
5. **反思：** 方案的代价、局限、下一轮可能优化点。

可选主题：GAS Ability 生命周期、DataAsset 配置组织、建筑 Footprint/合法性、资源扣费与补偿、Replication 的使用范围、Late Join。**只有实际实现并核对后才纳入对应项目案例。**

## 5. 验证和未解决问题

| 项目 | 需要记录 |
| --- | --- |
| 验证环境 | 引擎具体版本 / Commit 或构建版本 |
| 验证步骤 | 明确可以复现的交互步骤 |
| 结果 | PASS / FAIL / NOT RUN，不能用模糊“都没问题” |
| 范围 | 被证实的是哪个系统、哪项能力，而非整个工程 |
| 已知限制 | 尚未实现、未测试、不支持的情况 |
| 后续计划 | 区分设想与已完成工作 |

如声称“测试通过”，必须能在相应报告里追溯测试名称、执行日期、范围和输出，不能用截图替代多玩家网络验证。

## 6. 原创与协作声明

- **Owned**：本人设计/实现/维护，必须核对实际代码提交与功能边界。
- **Integrated**：基于第三方、引擎、模板或其他同学的系统进行接入、改造。
- **Referenced**：学习借鉴的设计思想，不等于实现或贡献。
- **Not tested**：理解原理、功能存在但尚未独立测试；绝不能改写成「成功通过测试」。

不要公开受限团队仓库与被要求保密的截图；对外的代码片段可裁剪、脱敏，并标注来源边界。

## 7. 案例发布前检查

- [ ] 第一屏明确我做了什么，而不是只有游戏名称。
- [ ] 有真实可读的封面图，视频不是首屏阻塞资源。
- [ ] 技术机制可被有经验的 UE 面试官追问且自洽。
- [ ] 所有数据、指标、版本、运行结果与证据匹配。
- [ ] 与简历上的职责一致，不为作品集抬高贡献。
- [ ] 外链可访问；未公开代码不伪装成可点击链接。
- [ ] 不包含敏感素材、内部路径和不允许公开的资产。
